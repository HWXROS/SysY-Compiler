# SysY 编译器项目 · 面试指南

> 基于北大 MiniC 课程实现的 SysY (C 子集) 编译器
> 覆盖词法分析 → RISC-V 汇编生成全流程，通过 22 个 lv9 测试用例中 8 个

---

## 一、一句话介绍

> **"这是一个从零实现的 SysY 编译器。前端用 Flex/Bison 做词法语法分析生成 AST；中端将 AST 翻译成 Koopa IR（类 LLVM IR 的 SSA 中间表示）；后端生成 RISC-V 汇编并实现了简单的寄存器管理。核心难点在数组语义的正确实现和控制流图的结构化构造。"**

---

## 二、项目架构速览

```
源文件 (.c)
   ↓ 词法分析 (Flex)
   ↓ 语法分析 (Bison)  →  AST（抽象语法树）
   ↓ IR 生成（手写）    →  Koopa IR（SSA 形式中间表示）
   ↓ 目标代码生成      →  RISC-V 汇编 (.s)
```

## 三、核心 Challenge 故事库

### 故事一：Dangling Else 文法冲突

| 维度 | 内容 |
|------|------|
| **出处** | Lv8 合并 if-else 和多函数支持时 |
| **现象** | Bison 报 `"syntax is ambiguous"` |
| **根因** | `if (x) if (y) a; else b;` 中 else 不知道匹配哪个 if |
| **解决** | 将 Stmt 拆为 MatchedStmt 和 UnmatchedStmt 两个非终结符 |
| **启示** | 文法设计本身需要保证确定性，不能依赖 Parser Generator 自动处理 |

**关键代码**：
```yacc
MatchedStmt
  : IF '(' Exp ')' MatchedStmt ELSE MatchedStmt
  | /* 其他无歧义语句 */
  ;
UnmatchedStmt
  : IF '(' Exp ')' Stmt
  | IF '(' Exp ')' MatchedStmt ELSE UnmatchedStmt
  ;
```

**可延伸知识点**：
- LALR(1) 与 LR(1) 的 lookahead 局限
- LLVM 中如何处理 if-else (基本块条件分支)
- GLR 解析和 LALR 解析的取舍

### 故事二：IR 格式契约 —— `%name=` vs `%name:`

| 维度 | 内容 |
|------|------|
| **出处** | 生成 Koopa IR 时基本块标签格式错误 |
| **根因** | BasicBlock::Dump 输出 `%entry=`，Koopa 规范要求 `%entry:` |
| **调试** | 写最小 Koopa IR 文件试探解析器预期格式 |
| **启示** | IR 格式是前后端间的严格协议契约，格式检查是编译器可靠性的第一道防线 |

**可延伸知识点**：
- LLVM 的 `.verifier` pass 设计意图
- IR 作为"contract"的设计原则
- 序列化/反序列化中的格式一致性问题
- SSA 形式中 label 的语义

### 故事三：控制流图的良构性 —— 不可达基本块与终止符

| 维度 | 内容 |
|------|------|
| **出处** | if-else 分支都有 return 时仍创建 end 块 |
| **根因** | 未检查 then/else 分支的最后一个基本块是否有 terminator |
| **解决** | HasTerminator() 检查 + 只在需要时创建 end 块；非 void 函数自动补 `ret 0` |
| **启示** | 编译器应在 IR 生成阶段就保证控制流图的良构性 |

**关键设计**：
```cpp
bool HasTerminator() const {
    if (insts.empty()) return false;
    auto last = insts.back().get();
    return dynamic_cast<RetInst*>(last) ||
           dynamic_cast<JumpInst*>(last) ||
           dynamic_cast<BranchInst*>(last);
}
```

**可延伸知识点**：
- 基本块的 terminator 在 SSA 和 CFG 中的核心地位
- LLVM 的 DominatorTree 分析依赖 CFG 完整性
- 死代码消除（DCE）如何利用不可达块信息
- 编译器"逐层保证正确性"的架构哲学

---

### 故事四：数组参数 —— C 指针语义的编译器实现

| 维度 | 内容 |
|------|------|
| **出处** | 多维数组作为函数参数时的传参和访问 |
| **根因** | C 语言中数组参数退化为指针，但语法上看起来像数组 |
| **难点** | `arr[i]` 在不同上下文中语义不同：参数传指针 vs 元素取值 |
| **方案** | 符号表维护参数数组标记；调用处判断 LVal 是否带下标；参数表声明为 `*i32` |
| **启示** | LLVM GEP 指令的逐层解引用设计就是为了保留类型结构信息 |

**核心思路**：
```cpp
// 参数声明时
if (param_ast->is_array)
    func->AddParam(param_ast->ident, "*i32");

// 调用时判断：数组名无下标 → 传指针
if (dynamic_cast<LValAST*>(args[i]))
    if (IsArray(lval->ident) && lval->indexes.empty())
        need_ptr = true;

// 函数体内访问：逐层 getptr
// arr[i][j][k] → getptr arr, i → getptr res, j → getptr res, k → load
```

**可延伸知识点**：
- C 语言的「数组退化为指针」语义（array decay）
- LLVM `getelementptr` GEP 指令的设计原理
- 胖指针（fat pointer）方案 vs 裸指针方案
- 类型系统在 IR 中的表达方式

---

### 故事五：while 循环与 break/continue —— 嵌套控制流管理

| 维度 | 内容 |
|------|------|
| **出处** | while 循环 + break/continue 的基本块生成 |
| **难点** | break/continue 需要作用于最近一层循环；return 时不再回跳 |
| **方案** | LoopContext 结构体 + 全局 loop stack 追踪嵌套关系 |
| **启示** | LLVM 的 LoopInfo pass 在 IR 生成阶段就需要对应的设计 |

**关键设计**：
```cpp
struct LoopContext {
    BasicBlock* cond_block;  // continue → 跳到这里
    BasicBlock* end_block;   // break → 跳到这里
};
thread_local std::vector<LoopContext> g_loop_stack;
```

**可延伸知识点**：
- LLVM 的 LoopInfo、LoopSimplify pass
- 结构化控制流 vs 任意 goto 的 CFG 表示
- 回边（back edge）和自然循环（natural loop）
- 支配树分析与循环识别

---

### 故事六：RISC-V 后端的"软件寄存器" —— 从全部 spill 到引用计数

| 维度 | 内容 |
|------|------|
| **出处** | 后端汇编生成中寄存器管理策略 |
| **难点** | IR 有上百个虚拟寄存器，RISC-V 只有少量物理寄存器 |
| **方案** | 引用计数优化：先遍历 IR 标记被多次引用的值，只对这些值做 spill |
| **启示** | 内存访问比寄存器运算慢两个数量级，寄存器分配是编译器后端最核心的优化 |

**可延伸知识点**：
- 线性扫描寄存器分配（Linear Scan）算法
- 图着色寄存器分配（Graph Coloring）算法
- Caller-saved vs Callee-saved 寄存器
- Spill cost 模型
- LLVM 的寄存器分配器架构

## 四、面试追问分类准备

### 🔵 基础知识类

**Q: 什么是 SSA 形式？为什么用 SSA？**
> SSA（Static Single Assignment）要求每个变量只赋值一次。好处：(1) 每个变量只有一个定义点，数据流分析变得简单；(2) 使用-定义链（use-def chain）隐式建立；(3) 使很多优化（常量传播、死代码消除）更高效。LLVM IR 和我的 Koopa IR 都采用 SSA 形式。

**Q: 讲一下你的符号表设计**
> 采用作用域链（scope chain）方式：每个符号表有 parent 指针指向外层作用域。查变量时从当前层向上递归查找。存储信息包括：常量值、变量地址、是否为数组、是否为全局变量、函数参数数组标记等。函数定义时创建新的符号表，parent 指向上层。

**Q: 怎么处理 const 变量？**
> const 变量在编译期求值（常量折叠）。AST 生成 IR 时，如果是 const 表达式且所有操作数都是常量，直接计算出结果返回 IntConst，不生成 IR 指令。ConstDefAST 在编译期将值存入符号表。

### 🟡 编译器设计类

**Q: 为什么选择自己手写 IR 而不是直接用 Koopa 的 API？**
> 灵活性考虑。手写 IR 让我可以：(1) 更自由地控制指令序列，方便后续优化；(2) 自己做寄存器分配时能维护额外的元信息；(3) 深入理解 IR 设计的底层逻辑。生成的 IR 文本通过 Koopa 的 parser 再转成 Koopa raw program，相当于用 Koopa 做了 IR 的验证。

**Q: 如果让你加一个优化 pass，你会加什么？**
> 常量折叠和常量传播（Constant Folding & Propagation）。在 IR 层面遍历所有指令，如果二元操作的两个操作数都是常量，直接计算结果并替换。这是最安全也最简单的优化。其次是死代码消除（DCE）—— 如果一个值的所有引用都被替换后，定义它的指令就可以删除。

**Q: 你的 IR 和 LLVM IR 有什么异同？**
> 共同点：都是 SSA 形式、都有基本块和 terminator 概念、`getptr` 对应 LLVM 的 `getelementptr`。差异：我的 IR 简化了很多——没有 phi 指令（通过控制流结构保证）、没有向量类型、没有内存操作数的访存对齐信息。本质上是教学级 IR 和工业级 IR 的差距。

### 🔴 语言语义类

**Q: SysY 和标准 C 的主要区别？**
> SysY 是 C 子集，去掉了指针算术、结构体、switch、goto、位域等。保留数组、函数调用、控制流。常量表达式必须是编译期可计算的（无运行时计算）。

**Q: 数组初始化怎么实现的？**
> 支持 `int arr[2][3] = {{1,2,3},{4,5,6}}`。用 InitListAST 表示初始化列表，IR 生成时展开为逐个元素的 store 序列。关键是要处理嵌套展开规则：最里层的列表对齐到元素级别，外层对应到子数组。

**Q: void 函数怎么处理的？**
> 函数定义时标记 is_void。IR 生成时：void 函数不生成返回值分配；ret 指令无操作数；调用 void 函数时不创建接收返回值的 IR 变量。Koopa IR 中用 `fun @name()` 和 `fun @name(): i32` 区分。

### 🟣 后端/优化类

**Q: RISC-V 调用约定是怎样的？你的编译器怎么处理的？**
> Caller-saved 寄存器：t0-t6（临时寄存器）、a0-a7（参数寄存器）。Callee-saved 寄存器：s0-s11（保存寄存器）。函数参数通过 a0-a7 传递，返回值通过 a0。我的编译器在后端处理函数调用时，先递归计算每个参数的值放入 a0-a7，超过 8 个的参数通过栈传递。

**Q: 怎么处理寄存器不够用的情况（spill）？**
> 实现引用计数策略：遍历 IR，标记每个值被后续引用的次数。只将被多次引用的值 spill 到栈上。当寄存器耗尽时，将当前寄存器内容保存到栈（sw），后续使用时再加载（lw）。

**Q: 你的汇编生成是怎么从 Koopa IR 到 RISC-V 的？**
> 两种路径：(1) 通过 Koopa C API 将 IR 字符串解析为 `koopa_raw_program_t`，然后 RiscVGenerator 遍历 raw program 结构生成汇编；(2) 手写的后端直接处理我自己的 IR 结构，可以做更复杂的优化如寄存器分配。

## 五、向算子开发岗位建立连接

### 关键连接点

| 编译器概念 | 算子开发对应概念 |
|-----------|----------------|
| IR 设计（多层 IR 抽象） | TVM 的 Relay IR → TIR → 硬件后端 |

| getptr 地址计算 | TVM 中的 shared memory tiling + 访存优化 |
| 寄存器分配 + spill | GPU 中 shared memory / register 资源管理 |
| 基本块 + 控制流图 | 算子调度中的 loop nest + 并行化分析 |
| 常量折叠优化 | 算子融合中的常量表达式提前计算 |

### 面试话术

> "这个编译器项目的 IR 设计思想可以自然迁移到 TVM 等深度学习编译器中。比如我的 Koopa IR 是多层 IR 中的 low-level IR 层，对应 TVM 的 TIR——都是贴近机器的指令级表示。数组地址计算（getptr）的经验让我理解 TVM 里怎么处理张量访问的指针运算。寄存器分配的本质是在有限资源下做时分复用，这个思路在 GPU 算子开发中一样适用——shared memory、register file 都是有限资源，需要类似的分配策略。"

## 六、面试现场 · 完整讲法示例

### 1 分钟速讲版

> "这是我基于北大 MiniC 课程实现的 SysY 编译器。前端用 Flex/Bison 做词法语法分析生成 AST；中端把 AST 翻译成 Koopa IR（类 LLVM IR 的 SSA 形式）；后端生成 RISC-V 汇编。我主要负责数组特性的完整支持：多维数组的地址计算、数组参数传参（数组名退化指针的语义处理）、嵌套初始化列表。项目中我深入理解了三个核心问题：IR 设计作为前后端的契约、C 语言类型系统的编译器表达、以及控制流图的结构化构造。通过了 22 个 lv9 测试用例中的 8 个（基本数组声明/访问/初始化/参数），剩余 14 个涉及大数组、常量数组、复杂多维参数和排序算法等高级场景。"

### Challenge 深讲版（以数组为例）

> "C 语言中数组作为函数参数时退化为指针，这个语义说起来简单，但编译器实现起来有很多细节。比如 `void f(int a[][10])` 中参数 a 在参数表里是指针，在函数体里 `a[i][j]` 又是下标访问。我的解决思路是三步：第一，在符号表里记录每个函数的哪些参数是数组；第二，调用时判断实参是不是数组名且没有下标，如果是就传指针（调用 GenIRPtr），否则传值；第三，函数体内用 getptr 逐层解引用计算地址。这个过程中我理解了 LLVM 为什么要把 GEP 设计成逐层求地址的形式——因为只有保留类型结构信息，编译器才能正确处理多维数组的偏移量计算，而不是在语义分析阶段就把所有信息拍平成线性偏移。"
