### 06_long_array — 大数组栈空间不足

- **源文件**：`int arr[4096] = {1};`
- **根因**：RISC-V 后端为局部数组分配了栈空间，但 `alloc_max_idx` 只根据 getptr 索引的最大值分配，对于 `4096` 个元素需要 `16384` 字节。当前后端在函数入口没有预留栈帧空间，只靠逐次 `stack_size -= N` 产生偏移，但这些偏移超过 `2047` 时虽然修复了 `lw/sw` 的大 offset 问题，但分配的空间仍然在栈上，`addi sp` 也需要预留空间。
- **修复方向**：在函数入口统一预留栈帧（`addi sp, sp, -frame_size`），在 `ret` 前恢复。

### 08_arr_access — 全局数组访问

- **源文件**：`int ga[10], gb[2][3] = {5,6,7,8};` + 局部数组 + 嵌套 while 循环
- **根因**：全局数组的初始化（`gb[2][3] = {5,6,7,8}`）在 IR 生成中表示为 `global @gb = alloc i32, 0`（只分配了 4 字节），因此访问 `gb[i][j]` 时地址计算错误。
- **修复方向**：全局数组需要正确的类型信息来计算总大小，`AddGlobal` 方法需要能指定数组总大小，或后端对全局数组采用不同的访问方式。

### 09_const_arr_read — 常量数组元素读取

- **源文件**：`const int arr[10] = {1, 2, 3, 4, 5};` + `sum = sum + arr[i] + garr[i];`
- **根因**：`ConstDefAST::GenIR` 只将常量值存入 `symtab.const_values[ident]`，没有为数组类型生成 IR（alloc + store）。当 LVal 访问 `arr[i]` 时，既不是 const（因为没有在 const_values 中记录下标对应的值）也不是 var（因为没有 alloc），导致返回默认值。
- **修复方向**：常量数组应在符号表中记录完整的初始化值列表，并在 IR 生成阶段像变量数组一样分配内存并初始化（编译期常量可以折叠）。

### 10_arr_in_loop — 循环体内的数组声明

- **源文件**：`while (i < 10) { int x[10] = {}; ... }`
- **根因**：循环体内的局部数组声明，每次迭代重新分配。当前 IR 生成在基本块内顺序插入 alloc 指令，但 Koopa IR 规范要求 alloc 必须在基本块开头。部分后端可能因 alloc 不在基本块开头而报错或行为异常。
- **修复方向**：IR 生成器应将循环体内的 alloc 指令提升到函数入口基本块开头。

### 12_more_arr_params — 复杂数组参数（10 个参数）

- **源文件**：`int f1(int a0[], ..., int a9[])` 和 `int f2(int a0[][10], int a1[], int a2, ...)`
- **根因**：10 个参数中部分为数组（传指针）、部分为标量（传值）。当前存在参数重命名（避免全局变量冲突）但 IR 生成阶段对标量参数的 alloc/store 引用名与函数参数名可能不一致。
- **修复方向**：排查 `rename_map` 机制是否完整作用到所有标量参数和数组参数的引用场景。

### 13_complex_arr_params — 三维数组参数

- **源文件**：`void init(int arr[][10][10])` 和 `int f2(..., int a5[][10][10], ...)`
- **根因**：三维数组作为参数传递时，地址计算需要多层 getptr（`base → [i] → [j] → [k] → load`）。当前 `LValAST::GenIR` 中对多维数组参数的处理可能存在 stride 计算错误。
- **修复方向**：当数组作为参数时，`var_addrs[ident] = -1` 且 `is_global = true`，后续访问通过 `@param_name` 引用。多层 getptr 的链式调用需确保每层索引乘的 stride 正确。

### 14_arr_lib_funcs — 库函数 getarray/putarray

- **源文件**：`int n = getarray(arr);` 和 `putarray(n, arr);`
- **根因**：`getarray` 从 stdin 读取数组长度和元素并填充到数组中，返回元素个数。当前实现可能没有正确处理 `arr` 作为数组名（传指针）传给 `getarray` 的语义。
- **修复方向**：检查 `CallExprAST::GenIR` 中对 `getarray`/`putarray` 参数的处理，确保数组名作为实参时传递的是指针而非元素值。

### 15-21 排序算法 — 综合数组操作

- **包含**：冒泡排序、快速排序、堆排序、计数排序
- **根因**：综合了以上所有问题——全局变量（`int n`）、数组参数（`int arr[]`）、多维访问、数组元素赋值。每个排序都有不同的 bug 组合。
- **修复方向**：先修复上述基础问题，再逐一排查各排序测试。

## 其他已知问题

1. **RISC-V 后端栈帧管理**：当前没有统一栈帧分配，`stack_size` 在函数入口处不预留空间，靠逐条指令累积。大数组场景下 stack_size 变得非常大。
2. **IR 生成器数组类型缺失**：`AllocInst` 只生成 `alloc i32`，没有 `[N x i32]` 的数组类型支持。Koopa IR 支持数组类型但当前 IR 生成器没有利用。
3. **`alloc_max_idx` 保守估计**：对于变量索引（`arr[i]`）的 getptr，默认只分配 4096 个元素（16384 字节），超出则溢出。
4. **`VisitGetPtr` 对链式 getptr 的处理**：当多个 getptr 链式调用时（如 `getptr→getptr→store`），中间结果被保存到栈上，但后续加载时可能是地址值也可能是整数值，当前已通过区分 `KOOPA_RVT_ALLOC` 和栈上值来修复，但可能仍有边界情况。
